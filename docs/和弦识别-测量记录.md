# 和弦识别：测量记录与结论

> 起因：用户反馈"AI 扒谱对和弦的识别不准确"。
> 测量脚本（可复跑）：`app/integration_test/chord_accuracy_test.dart`
> ```
> cd app; flutter test integration_test/chord_accuracy_test.dart -d windows
> ```

## 怎么量的

用**内置的真实钢琴采样**（Salamander，见 `tool/fetch_piano_samples.mjs`）渲染已知和弦进行，
真值完全可控（音高、起始时间、时值都是我们自己写进去的），再喂给 Basic Pitch，
逐个和弦算：

- **recall** = 该响的音里检出了几个（漏音就是"和弦错了"）
- **precision** = 检出的音里有几个是真的（多出来的就是鬼影/幻觉）

## 基线（修正测量方法之后）

| 场景 | recall | precision | 多出来的音 |
|---|---|---|---|
| 三和弦 C-F-G-C（C4 E4 G4 …） | **100%** | 86% | C5（C4 的八度泛音） |
| 七和弦 Cmaj7-Dm7-G7-Cmaj7 | **100%** | **100%** | — |
| 低音 + 和弦（C3 + C4 E4 G4 …） | **100%** | **100%** | — |
| 开放排列（C3 G3 E4 C5 …） | **100%** | 73% | C4（C3 的八度泛音）、F4（F3 的八度泛音） |

**结论一：模型的"漏音"问题不存在** —— 真实钢琴和弦的 recall 是 100%。
"不准"的实际表现是 **precision**：多出**八度/十二度泛音鬼影**。

> 测量踩过的坑（值得记住）：第一版直接把 44.1kHz 的 WAV 喂给模型（模型要 22050Hz），
> 结果整体低一个八度、时间轴也差一倍，差点误判成"模型移植有 bug"。
> 现在测量走 App 自己的加载路径 `loadAudioFile()`（内部会重采样）。

## 试过但**否掉**的自动去鬼影方案

### 1) 响度 + 时长判据（否）

想法：鬼影比基音轻、而且短。实测数据（响度, 时长）：

| 音 | 值 | 判定 |
|---|---|---|
| 真 C5（低音+和弦里的和弦音） | (0.38, 0.26s)，基音 F3 (0.63, 0.98s) | 真 |
| 鬼影 C5（C4 的二次谐波） | (0.35, 0.21s)，基音 C4 (0.73, 0.98s) | 鬼影 |
| 真 C5（开放排列最高音） | (0.34, 0.19s)，基音 C3 (0.79, 0.99s) | 真 |

真音与鬼影的数值**完全重叠**，任何阈值都会误删 → 启用后 recall 从 100% 掉到 88%，
所以**没有启用**这个判据（代码里保留了原来的、只用于主旋律模式的保守版本）。

### 2) 频谱残差验证（否，实现保留但默认不启用）

想法：鬼影的能量完全来自低音的某次谐波，而真音会在此之外多出一份能量。
做法 `lib/transcribe/spectral_verify.dart`：

1. 取候选音起音后 20ms 的一小段做 FFT；
2. 用低音**其它分音**（避开所有已检出音的基频）在 log-log 上**局部插值**，
   预测"候选音频率处本该有多少能量"；
3. 只有"实测明显高于预测"（有残差）才认为是真音。

实测：
- **全局幂律拟合**版本太糙 → 把真的和弦音也删了（低音+和弦 recall → 56%）；
- 改成**局部插值**后 recall 恢复到 100%，但一个鬼影也去不掉
  （鬼影处的实测能量确实高于插值预测——钢琴低音的谐波本身起伏就很大）；
- 加上"必须同时明显更轻"的交集条件后：**recall 100%、precision 与不处理时完全一样**（86/100/100/73）。

**结论二：以现有信息（单帧幅度谱）无法可靠区分"真八度叠置"与"泛音鬼影"。**
要真正分开，需要更细的声源模型（逐音估计谐波幅度包络 + 衰减率/相位，
甚至分离出每个音的起音瞬态），属于研究级工作量，不适合塞进手机端实时流程。

## 最终做法：把判断交给用户

- 代码里保留 `mergeDuplicateNotes`（**已验证安全**：同一音高、**同一次触键**的重复检出合并；
  注意不能按"时间重叠"合并，否则会把同一个音在两个和弦里的两次弹奏并成一个长音——
  实测踩过：最后一个和弦的 G4/B4 整对消失）。
- 新增 `lib/core/chord_analysis.dart`：把每个和弦判读成 `C` / `Am7` / `G7`…，
  并标出**缺音 / 多音 / 八度重复**（八度重复正是鬼影的形态）。
- 乐谱页工具栏在有和弦时出现「和弦核对」入口，点开是逐条列表：
  `第 3 小节 · C（大三）  C4 E4 G4 C5 · 八度重复 C` —— 用户一眼能看出哪些要删。
- **不自动改谱**：自动删会连真的和弦音一起删（见上面的数据）。

## 顺带修掉的真 bug

- `analysisFromBasicPitch(melodyOnly: false)`（即"保留和弦"模式）以前**完全不做泛音清理**；
  现在复调模式会走频谱残差那条路（当前配置下等价于"不做改动"，但入口已经接好，
  以后换成更好的声源模型只改 `spectral_verify.dart` 一处）。

# 人声分离（可选包）的宿主契约

用户要求"**用伴奏转谱**，大小模型都做成可选，用户自己决策"。候选已登记为两个包
（`kSeparatorSmallPack` 50.8MB MIT / `kSeparatorLargePack` 172MB 许可未标注）。

小包用的是 UVR-MDX-NET **KARA2** 的 ONNX 图。实测（下载 50.8MB，2 秒）：

| 项 | 值 |
|---|---|
| 输入 | `input` float32 **[1, 4, 2048, 256]** —— 4 = 立体声 × (实部, 虚部) |
| 输出 | `output` float32 同形状（掩蔽后的频谱，**不是波形**） |
| 采样率 | **44100 Hz 立体声**（不是 16k/22.05k） |
| STFT | `n_fft 5120`、`hop 1024`、**periodic Hann**（`0.5-0.5cos(2πn/N)`）、
帧居中 + **reflect padding `n_fft/2`** |
| 频谱截取 | 2561 个 bin 里取**前 2048 个**，且 **bins 0..2 置零** |
| 分块 | 一块 = **256 帧 = 261,120 样本**（batch 1，静态形状） |
| 反变换 | 输出后 **bins 2048..2560 置零** → iSTFT → 逐块 overlap-add |
| 图优化 | **开/关结果完全一致**（sum/min/max 逐位相同）✓ → 不受
"Flutter 插件关不掉图优化"的限制 |
| 速度 | **~3.5s/块（5.9 秒音频）→ 0.59× 实时**（桌面 CPU；手机更慢 ✗） |

**结论**：这个模型不像 CRNN/Tsumugi 那样"波形进、音符出"，**Dart 侧必须自己实现
STFT/ISTFT（含 Hann、reflect-center padding、bin 截取与置零、逐块 overlap-add）**，
约 250 行 + 单测；跑完再走现成的扒谱链路。

> 这里又一次印证了"先查现成方案"：契约参数若靠猜（n_fft/hop/窗口/置零规则），
> 出来的会是噪声而不是人声——模型卡把契约写得很死（"A different window, bin count
> or channel order gives wrong output"）。

# CRNN 扒钢琴谱"音不对"的排查记录（用户反馈）

分两步做**可复现的对照**，把嫌疑范围缩到最小。

**第一步：引擎与物理量对照**（`integration_test/crnn_real_audio_probe_test.dart`）
90 秒真实钢琴录音，把"模型检出的音高"与"同一时间窗内音频频谱的峰值音高"逐窗比对
（频谱独立于模型，是硬对照）：

```
0s   模型: F#5 G#5 C#6 D#6 F6 A#6          | 频谱: F6 F#5 G#5 C#6 D#6        ✓
24s  模型: A#4 F5 C6 C#6 D#6 C7            | 频谱: C#6 D#6 A#4 C6 G#5        ✓
60s  模型: A#2 F3 G#3 A#3 C#4 D#4 F4 G#4   | 频谱: F4 G#4 D#4 A#3 G#5        ✓（低音更全）
```

→ **引擎没有系统性错误**（采样率、键位 21+k、帧率 100fps、张量取用都对得上）。

**第二步：走完整 App 管线的音高保真度**（`integration_test/crnn_pipeline_fidelity_test.dart`）

```
引擎检出 435 个音（32 种音高） → 量化+双谱表乐谱 323 个音（32 种音高）
音高种类：丢失 0 / 多出 0     音高重合率 100.0%     估计 bpm 106 调 G#
```

→ **下游管线也不改音高**（个别音在乐谱里出现次数变多，是长音被小节线拆开，正常）。

**顺带修掉一个真 bug**：读输出张量用"名字包含"匹配 `frame` 会命中
**`pedal_frame_output`**（踏板那一路）✗ → 音长判定（`frame_disappear`）用的是错张量。
现已改为**精确名优先 + 排除 pedal** ✓。

**结论**：音高这条链路可信，剩下的嫌疑集中在**输入素材与调号**：
1. CRNN 是**钢琴独奏专用**——喂流行歌混音/带人声素材会明显变差（该换 Basic Pitch 或 Tsumugi）；
2. **调号是自动估计的**（上面那段真钢琴被估成 G#），所以**简谱数字**可能"看着不像"——
   扒谱页可手动指定调号，"按实际音高记谱"的五线谱本身不受影响；
3. 录音若整体跑调/移调，所有音一起偏，需按听感核对。

# MNN 后端：实测结论（官方工具链，命令照官方文档）

用户要求"查官方文档把 MNN 后端做进去"。先做了**前提验证**（脚本 `tools/onnx_export/mnn_probe.py`）：

```
转换： MNNConvert -f ONNX --modelFile X.onnx --MNNModel X.mnn --bizCode lipu
      （pip install MNN 自带 mnnconvert.exe，官方文档原文）
推理： MNN.Interpreter + createSession({"backend": "CPU", "numThread": 4})
```

| 模型 | 转换 | 转换后运行 | 失败原因 |
|---|---|---|---|
| ByteDance CRNN | ✅ 147.1MB → **164.1MB .mnn**（2 秒） | ❌ | `Compute Shape Error for While119` / `Can't run session because not resized` —— **图里有控制流 `While`**，MNN 的 ONNX 前端不支持 |
| Tsumugi（自导出） | ✅ 3.6MB → **87.6MB .mnn**（2 秒） | ❌ | `Compute Shape Error for val_412`，且只返回一路输出（`(431,)` 的 `frame_valid_mask`），数值不可用 |

**结论：MNN 后端在这两个模型上不是"换个运行时就能跑"** —— 转换能过、运行过不去，
卡点在 MNN 的 ONNX 前端（控制流与形状推导），不在运行时本身。

剩下的路都要更大投入且收益存疑：
1. 走 **TorchScript 前端**（`-f TORCH`）：要原始 PyTorch 权重 + 自己写 trace 脚本——
   Tsumugi 权重我们有 ✓（14M 参数），CRNN 只有别人转好的 ONNX ✗；
2. 改图（把 `While` 展开成静态子图）——属于逆向别人的导出 ✗；
3. 先算收益：本机实测 GPU/DirectML 对这类小模型是**负收益**（CRNN 13.7s vs CPU 11.6s），
   "上 NPU"的动机本身不成立；真要提速，Tsumugi 的"按激活挑音高"更实在。

### 决策（用户）：能直接用的就用 onnxruntime，MNN 只留给"非它不可"的模型

- 两个已接通的后端（CRNN / Tsumugi）都在 **onnxruntime** 上验证过数值与速度 → **不走 MNN**；
- MNN 保留为 `InferenceRuntime.mnn` 这一档，**只有 ORT 加载不了的模型**才声明它；
- 代码里已落成一条**约束测试**：注册表内所有后端必须声明 `onnxRuntime`
  （`app/test/model_packs_test.dart` 的「运行时策略」用例），将来有人误接 MNN 会被测出来。
> 附带事实：MNN 的 Android 核心 so 约 **800KB**（官方 README），NPU 后端有
> QNN / Hexagon(3.6.1) / NNAPI —— **接入成本不高，卡的是模型转换**。

# 高精度扒谱后端（可选包）实测


用户要求接入两个"准确率更高的后端"，都做成按需下载的可选包。逐项实测记录如下。

## 1. ByteDance 钢琴 CRNN（可选包，已接入）

模型：Kong et al. 2021（IEEE/ACM TASLP），MIT，ONNX 147.1MB，
输入原始波形 `[1,160000]`（16kHz / 10 秒，mel 前端在图里），输出 `reg_onset/reg_offset/frame/velocity`
各 `[1,1001,88]` + 三路踏板。

同一套和弦基准（App 自己的 Dart 引擎跑真模型，`integration_test/crnn_pack_e2e_test.dart`）：

| 场景 | Basic Pitch | CRNN（App 引擎） |
|---|---|---|
| 三和弦 | 100% / 86% | 100% / 75% |
| 七和弦 | 100% / 100% | 100% / 94% |
| 低音+和弦 | 100% / 100% | 100% / 84% |
| 开放排列 | 100% / 73% | 100% / 80% |

**recall 都是 100%，precision 互有高低**（CRNN 多出来的是"和弦音的高八度"，Basic Pitch 多的是"低音的八度"）。
速度：90 秒真实钢琴录音 11.6s（0.13× 实时，桌面 CPU）。
**DirectML 走 GPU 反而更慢（13.7s vs 11.6s）** —— 小 CNN+BiGRU 的瓶颈是算子调度不是算力。

### 解码器的坑（靠数据一步步定位）

| 解码策略 | recall | precision |
|---|---|---|
| 逐帧判 onset（Node 探针版） | 100% | 86% |
| 「连续帧取峰」 | **93%** ✗ | — |
| 「连续帧整段合并」 | **95%** ✗ | — |
| 逐帧判 + 同一次触键合并 + offset 至少晚 30ms（自创） | **100%** ✓ | 83% |
| **官方解码器 1:1 移植**（邻域去抖 + 帧消失/offset 取舍） | **100%** ✓ | 83% |

真因：模型对 B4 在 299~304 帧**连续**报 onset，而 offset 落在 302 帧 —— 配对出一个 20ms 的假音，
被"最短时长 30ms"滤掉，**整个音消失**。

**但真正的教训不是这个 bug，而是"该先查现成方案"**：官方解码器（`piano_transcription_inference`
的 `RegressionPostProcessor`）一直是公开的，我却是靠试错收敛到近似行为的。移植后对照，我原先有三处
与官方不一致（都在 `lib/transcribe/crnn_engine.dart` 里改正了）：

1. **帧内位置**：我以为 `reg_onset` 的值就是帧内位置，官方是用左右邻帧算
   `shift = (x[n+1]-x[n-1])/(x[n]-x[n±1])/2`；
2. **邻域去抖**：官方要求 `is_monotonic_neighbour`（左右单调）才算事件 —— 这正是我"取峰/整段合并"
   两种写法都在近似的东西；
3. **结束时间**：官方在 `offset_occur` 与 `frame_disappear` 之间按"谁靠近消失点"取舍，
   而不是"最短时长"这类硬阈值（实测：offset 太早反而应取 frame 消失点）。

移植版与自创版在本基准上打平（100% / 83%），但语义与上游一致、可维护，
并且**踏板通路（`pedal_frame_output` / `reg_pedal_onset/offset`）已经具备**——真实钢琴录音里，
踏板会延长音的时值，这是合成测试看不出来的收益。


### int8 量化：实测失败，已放弃

| | fp32 | int8 动态量化 |
|---|---|---|
| 体积 | 147.1MB | 113.5MB（只有 1.3×，**不是** 4×） |
| 音符数 | 74 | **17** ✗ |
| 起音一致 | — | **10/74** ✗ |
| 单段耗时 | 1192ms | **13050ms**（慢 11 倍）✗ |

原因：这个网络的参数大头在 **Conv**（CRNN 的 CNN 部分），而 ORT 的 `quantize_dynamic`
只量化 MatMul/Attention 权重，所以体积几乎没降；RNN/Conv 混合图跑动态量化权重还更慢。
要继续压体积得上 `quantize_static` + 校准集（能覆盖 Conv），但需要先验证精度 ——
在验证通过之前，**可选包就用 fp32（147MB，按需下载）**，不发布这个坏模型。
脚本与对比口径留在 `tools/onnx_export/quantize_crnn.py`。

## 3. 教训与"先查现成方案"

这一轮的弯路值得记下来：

**CRNN 的解码器我一开始是"自己发明"的**，结果连撞两次墙（连续帧取峰 → recall 93%；
整段合并 → recall 95%），最后靠打印模型原始张量才定位到真因
（连续 onset 帧 + 贴脸 offset → 20ms 假音被最短时长滤掉）。

**而现成的实现在那儿摆着**：

| 现成方案 | 位置 | 用途 |
|---|---|---|
| ByteDance 官方解码器 `RegressionPostProcessor` | `third_party/piano_transcription_inference/utilities.py`（官方 PyPI 包 `piano_transcription_inference==0.0.6`，已固化进仓库） | **含踏板检测 + `frame` 校验 + 邻域去抖**的完整解码；Dart 侧应当按它 1:1 重写（当前是简化版） |
| MobiMML（浏览器里跑同一个 CRNN） | `github.com/Mobi-Lan/MobiMML` + HF `LanOss/mobimml-piano-transcription` | 一份**已经跑通的 JS 实现**，可用来交叉验证解码行为 |
| Tsumugi 自己的解码入口 | `inference/v1_windowed.py: decode_v1_notes()`（约 280 行）+ `modeling/heads/semi_crf.py: decode_pitch_intervals()` | Dart 侧半-CRF DP 的移植蓝本；`semi_crf_backend` 只有 `torch` / `triton` 两种（后者要 CUDA），**没有** NumPy 参考实现，所以只能照 `torch` 那条路移植 |

移植清单（官方 `utilities.py`，按依赖顺序）：

```
output_dict_to_midi_events          → 总入口
  output_dict_to_note_pedal_arrays  → 音符 + 踏板数组
    output_dict_to_detected_notes   → 音符（onset/offset/frame/velocity 四路一起用）
    output_dict_to_detected_pedals  → 踏板
    get_binarized_output_from_regression(reg, threshold, neighbour) → 二值化 + 邻域去抖
      is_monotonic_neighbour        → 邻域单调性判断（这就是我缺的那一步）
  detected_notes_to_events / detected_pedals_to_events
```

关键差别（当前 Dart 简化版缺的）：
1. **邻域去抖**：`is_monotonic_neighbour` 会把"连续几帧都超阈值"压成一个事件 ——
   我手写的版本要么全收（重复音）要么取峰（漏音），正确做法是官方这个判断；
2. **`frame` 路校验**：真正决定音是否成立的依据，而不是我加的"最短时长"硬阈值；
3. **踏板**：`pedal_frame_output` / `reg_pedal_onset/offset` 会延长音的时值（钢琴真实演奏离不开）。

## 4. Tsumugi（乐器无关，半-CRF）

**原判断"导不出 ONNX"是错的**，实测可以导出（见下），教训同上：先试现成工具链。

### 导出结果（`tools/onnx_export/probe_tsumugi_export.py`）

| 项 | 结果 |
|---|---|
| 检查点 | `best_model.pth` 53.5MB，**14.0M 参数**，`model_state_dict` + `model_config` + `config` |
| 配置 | `sample_rate=22050`、`hop_length=512`、`semi_crf=v1`、`head_dim=256` |
| 输入 | **`[1, 2, T]` 双声道** 22.05kHz（固定段长；CQT 的 reflect padding 在动态形状下导不出） |
| 导出工具 | `torch.onnx.export(..., dynamo=True)` ✓（老 TorchScript 导出器过不了 `torch.stft` 的复数张量） |
| 产物 | `tsumugi_amt.onnx` 3.62MB + 外部权重 `tsumugi_amt.onnx.data` 55.1MB（自包含） |
| 数值 | 6 路输出相对误差 **1.1e-5 ~ 6.4e-5**，`frame_valid_mask` 布尔完全一致（**独立进程**复核 ✓） |

**关键结论**：`forward()` 里**没有解码** —— 半-CRF 的区间 DP 是独立一步
（`decode_pitch_intervals`），所以路线是"网络导出 + Dart 里移植 DP"，而不是整模型导出。

### 移植契约（照这三处 1:1 抄，别自己发明）

**入口**（`inference/v1_windowed.py: decode_v1_notes` → 第 250~262 行）：

```python
decode_pitch_intervals(
    outputs["interval_query"][b:b+1],   # ONNX 输出 1
    outputs["interval_key"][b:b+1],     # ONNX 输出 2
    outputs["interval_diag"][b:b+1],    # ONNX 输出 3
    valid_lengths[b:b+1],
    length_scaling=config.semi_crf_length_scaling,   # none/linear/sqrt（checkpoint 里是 none）
    length_penalty=config.semi_crf_length_penalty,
    note_bias=settings.note_bias,
    track_batch_size=settings.track_batch_size,
    forced_start_pos=...,               # 跨窗口拼接用，单窗口可为 None
    backend=settings.semi_crf_backend,  # 只用 "torch"（triton 要 CUDA）
)
```

**打分矩阵**（`modeling/heads/semi_crf.py`）：

| 量 | 来源 |
|---|---|
| 对角项（单帧分） | `interval_diag[t, k]`（`_flatten_interval_diag`，约 547 行） |
| 非对角项（区间分） | `interval_query[t, k, :] · interval_key[u, k, :]`（双线性点积） |
| 长度缩放/惩罚 | `_build_length_penalty`（约 590 行）+ `length_scaling ∈ {none, linear, sqrt}` |
| 偏置 | `note_bias`（加在"这是一个音"的分数上） |

**DP**（同文件）：`viterbi`（167 行）/ `viterbiBackward`（91 行）——
在帧轴上做**分段式**（segmental）Viterbi：每个音是一段区间 `[t, u]`，
段内不能重叠，`noiseScore` 是"这里没有音"的转移分（`_strictly_lower_triangular_mask` 约束 u>t）。

**要做的事**：把上面两块（打分矩阵 + 分段 Viterbi）用 Dart 重写，
输入就是已导出的 6 路张量里的 3 路，输出 `[start_frame, end_frame, pitch]` 列表，
再换成秒 → 复用现成的 `analysisFromDetectedNotes` ✓。

**已核对**：稀疏解码入口 `decode_pitch_intervals_sparse` 只需要
`interval_query / interval_key / interval_diag + valid_lengths`，
**没有额外的 noiseScore 输入**（"此处无音"的分数由图内 `softplus(score[end,end,:])` 之类构造），
所以**已导出的 6 路输出是够的**，不用重新导出 ✓。

**进度**：
- ✅ 区间打分矩阵已在 Dart 落地（`lib/transcribe/tsumugi_engine.dart: buildIntervalScores`）
- ✅ **分段 Viterbi 已落地**（`viterbiDecodeIntervals`，官方 `semi_crf.py: viterbi()` 的 1:1 移植）
- ✅ **`noiseScore` 官方是全零**（`_zero_noise_score`，源码 1507/1638/1784 行）——最后一个未知量清零
- ✅ **ONNX 引擎接通**（`TsumugiEngine`：双声道 22.05kHz、10 秒定长分段、
  用 `frame_valid_mask` + 真实音频长度裁帧、三路张量 → 打分 → Viterbi → 音符）

### 三个后端同台（同一套和弦基准，App 自己的引擎跑真模型）

| 场景 | Basic Pitch（230KB，内置） | ByteDance CRNN（147MB） | **Tsumugi（55MB）** |
|---|---|---|---|
| 三和弦 | 100% / 86% | 100% / 75% | **100% / 92%** |
| 七和弦 | 100% / 100% | 100% / 94% | **100% / 94%** |
| 低音+和弦 | 100% / 100% | 100% / 84% | **100% / 100%** |
| 开放排列 | 100% / 73% | 100% / 80% | **100% / 76%** |

**recall 三者都是 100%**；Tsumugi 体积只有 CRNN 的 37%，precision 反而更高（4 个场景里 3 个最好），
